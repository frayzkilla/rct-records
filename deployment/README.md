# HTTPS на VPS для rawcrownz.ru

Сертификат уже обслуживает Certbot, HTTPS завершается в Nginx хоста. Контейнер frontend доступен только через `127.0.0.1:3001`, backend и PostgreSQL не публикуют порты. HTTP между Nginx хоста и Docker остается локальным.

## Применение

1. Сохраните действующие параметры БД в `.env`: смена `DB_PASSWORD` в файле не меняет пароль существующего PostgreSQL. Для ротации нужна отдельная согласованная смена пароля в БД. `GOD_ADMIN_PASSWORD` также не сбрасывает пароль существующего аккаунта.
2. Пересоберите проект на VPS: `docker compose up --build -d`. Не удаляйте том `postgres-data` и каталог `storage`.
3. Проверьте путь сертификата командой `sudo certbot certificates`. В `nginx/rawcrownz.ru.conf` укажите действительные пути, если имя сертификата отличается. Конфигурация рассчитана на `rawcrownz.ru`; дополнительные имена, например `www`, требуют включения в сертификат и `server_name`.
4. Замените содержимое действующего виртуального хоста `rawcrownz.ru` в Nginx конфигурацией из `nginx/rawcrownz.ru.conf`. Не оставляйте параллельно старый виртуальный хост с тем же именем, особенно старый HTTP-прокси.
5. Проверьте `sudo nginx -t`, затем выполните `sudo systemctl reload nginx`.
6. Проверьте `sudo certbot renew --dry-run`. Для существующего метода `nginx` оставлен порт 80, где Certbot может временно обслужить проверку. Для метода `webroot` каталог в renewal-конфигурации Certbot должен совпадать с `/var/www/letsencrypt`; создайте его командой `sudo mkdir -p /var/www/letsencrypt` либо замените `root` в Nginx на уже используемый каталог. Если Certbot использует `standalone`, его hooks должны освобождать порт 80 на время проверки; удобнее отдельно настроить `nginx` или `webroot` и проверить dry-run.

Сайт и API доступны только по HTTPS. Обычные HTTP-запросы закрываются кодом Nginx 444, без выдачи страницы и без перенаправления. На порту 80 оставлен только `/.well-known/acme-challenge/` для продления сертификата. Полностью закрывать порт 80 можно после перехода Certbot на DNS-проверку: тогда удалите HTTP-блок и закройте порт в firewall.

## Адрес клиента и ограничения

Nginx хоста заменяет заголовки `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`. Nginx контейнера доверяет `X-Real-IP` только от сети `TRUSTED_PROXY_CIDR` (по умолчанию `172.16.0.0/12`, стандартные Docker bridge-сети). Если используется другой диапазон Docker, укажите в `.env` адрес шлюза контейнерной сети с маской `/32`, например `TRUSTED_PROXY_CIDR=172.20.0.1/32`. Адрес шлюза виден в `docker network inspect rct-records_app-network`; имя зависит от каталога Compose.

Не публикуйте порт backend: он доверяет forwarded-заголовкам внутреннего Nginx. Не меняйте loopback-привязку frontend на `0.0.0.0`.

Ограничение входа теперь действует по реальному IP, а не общему адресу Nginx. API ограничен по частоте, лайки — 30 запросами в минуту с небольшим burst. До разбора JSON действует лимит 64 KiB; multipart ограничен суммой двух файлов `MAX_UPLOAD_BYTES` плюс 64 KiB метаданных. Nginx дополнительно ограничивает загрузки 201 MiB: при увеличении `MAX_UPLOAD_BYTES` согласованно измените `client_max_body_size` в обоих Nginx. Эти меры сдерживают расход ресурсов, но не заменяют квоты хранения и защиту от распределенных атак.

## Проверка после обновления

В `frontend/package.json` Rollup закреплен через `overrides` на 4.59.0: с 4.64.0 локальная сборка зависала, с 4.59.0 проходит. Версия прошла `npm audit`; остальные обновления зависимостей сохранены.

```sh
curl -I https://rawcrownz.ru/
curl https://rawcrownz.ru/api/health
curl -v http://rawcrownz.ru/  # Ожидается закрытие соединения, не HTML сайта.
sudo certbot renew --dry-run
```

В браузере проверьте вход, загрузку и воспроизведение трека, лайки. Cookie `rct_admin_session` должна иметь Secure, HttpOnly и SameSite=Strict. С внешнего компьютера порты 3001 и 3002 должны быть недоступны. Если перед VPS установлен CDN или дополнительный proxy, доверие к его IP следует отдельно настроить на Nginx хоста; иначе ограничения будут считать адрес этого proxy.
